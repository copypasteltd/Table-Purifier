# 表格修复站：需求解读与检查

> 历史v1.0评审：本轮用户方向调整后已被v2.0替代。以下“当前”均指检查当时的旧基线；现行需求见[PRD](../01-产品需求PRD.md)，交互见[新方向设计](../设计/多源资料与规范表成表-2026-10-27.md)。

检查日期：2026-10-27。依据：当前五份主需求文档及共用支付、数据治理规范。本次检查与解读不替代 v1.0 基线，也不表示产品或支付功能已实现；下面明确区分现有要求和改进建议。

## 1. 当前需求的核心

产品处理的是订单表导入前的内容整理：用户提供来源表、目标字段模板和处理规则，系统生成新的可导入结果，并列出未解决记录、明确移出的记录和逐项修改依据。

此前方案把首版收敛到电商订单，是用于限制实现范围的产品假设；尚无用户访谈、真实目标系统验证或付费证据支持它。用户最初提出的“表格修复”可以覆盖更广场景，现有方案没有将广义表格问题全部纳入首版。损坏文件恢复、找回原文件已丢失的数字、任意 Excel 排版重建等，目前不在支持范围内。

用户购买的价值是少做重复整理、减少导入返工，并能查清每个改动，而非单纯获取一段 AI 建议。系统目标是按确认规则正确转换，不能保证源订单事实本来正确。

主文档共22项功能：20项P0首版要求、1项P1模板库/批量/连接器要求、1项P2新增领域/规格要求。当前 `src/` 尚无实现代码，原验收表也未执行。

## 2. 首批用户和购买时机

| 用户 | 具体任务 | 产品应提供的帮助 |
| --- | --- | --- |
| 电商运营/店主 | 把一种来源的订单表导入选定管理系统 | 配准字段和格式，提前识别无法导入的行，下载新文件 |
| 代运营/工作室 | 经常收到列名和格式不同的客户表格 | 用可追溯的配置处理重复工作，避免手工改错；复用模板的完整产品体验排P1 |
| 自动化/Agent开发者 | 在工作流内按需处理一次订单表 | 用结构化API完成上传、确认、付费、查询和领取，无须解析网页 |

目前还没有确定一个具体外部目标系统。首版即使按自定义模板生成合格文件，也只能声称“符合该模板”；真正承诺某系统可导入前，必须拿该系统的真实导入规范与结果验证。

## 3. 一个完整的使用过程

1. 上传来源文件。先检查类型、大小、表结构及能否安全解析；空表或不支持文件不收费。
2. 选择一个工作表、一个表头行和目标字段模板；同名来源列以不同列ID区分。
3. 免费诊断。列出缺失值、日期/金额歧义、重复候选、字段映射建议。规则检查覆盖全表；AI最多看到5条必要脱敏样本，不能据此冒充全表质量检查。
4. 确认处理规则。用户明确哪些来源列对应目标列、日期含义、金额分隔符、币种/精度和重复候选处理方法。无法确定的问题可保留为待确认，不能由模型猜值。
5. 看清结果范围和价格。比如“输入1000条，预计940条可导入、45条待确认、15条经你确认移出”；问题维度的统计可能相互重叠，最终三类去向不能重叠。
6. 按确定报价授权付款。当前实验价为1.9元/限定规格任务；尚未验证定价成立。支付、执行和结算顺序依实际获准Machine Pay接入冻结，不能凭前端成功提示发放付费权益。
7. 执行、验证并交付。按冻结规则转换全表，检查每条记录的去向、金额口径、导出格式和审计明细。完整结果包与规范摘要可领取，重复查询和下载原任务不再收费。
8. 导入与售后。用户在目标系统中导入；平台记录自愿提供的导入反馈。程序错误由平台纠错或退款，已知且事先明确的待确认项不应被宣传为“全部修好”。

例子中的数量纯属说明，不是真实订单、成功率或测试结果。

## 4. “修复”具体做什么

| 来源情况 | 当前要求 | 为什么需要确认或保留 |
| --- | --- | --- |
| 列名为“订单编码”，目标叫“订单编号” | 建议字段映射，用户确认后执行 | 列名语义相似不代表一定含义相同 |
| 文本订单号 `000123` | 保留文本和前导零 | 不能变成数字123 |
| 20位文本订单号 | 原字符串写入，XLSX明确用文本类型 | 避免输出时引入数字精度损失 |
| 单元格显示科学计数法 | 检查实际存储值与类型，不能仅凭显示断定已损坏 | 若原始数字确已丢失，不能靠模型恢复 |
| `2026/10/25` | 在确认的规则下转为目标日期格式 | 日期系统、时区、格式须符合模板 |
| `03/04/2026` | 未确认月日顺序时列待确认 | 可能是3月4日或4月3日 |
| `￥1,280.00` | 在已确认CNY及分隔规则下转换为规范金额 | 币种、精度和原值均须可追溯 |
| `1,280`，格式来源未知 | 先确认逗号含义 | 不能默认是1280，也不能默认是1.280 |
| 金额或必填日期为空 | 整行进入待确认，并给出原因 | 不将未知金额当0，不编日期 |
| 两行有相同订单号 | 标记候选，默认保留 | 同单不同商品可能是合法记录 |
| 用户明确要移出的某行 | 放入独立移出记录，保留理由/确认人 | 不静默删除，不让行数消失 |
| 目标XLSX中的危险文本 | 按字符串输出；CSV使用透明披露的安全处理 | 不能让文本在表格软件中成为执行公式 |

AI负责理解列名、提出映射和解释问题；代码按固定规则完成实际解析、转换、分组和导出。模型建议失败时允许手工配置。模型输出没有获得确认，不能变成整表改动。

实现时建议进一步明确源文件只读、生成独立新文件；现有追溯要求不应被解释为可以覆盖用户上传源文件。

## 5. 三类去向、交付和费用

每条非空输入记录恰有一个去向：

- 可导入：满足目标模板约束、相关歧义已解决的记录。
- 待确认：尚有不能确定或不满足约束的问题，显示原因与源坐标。
- 明确移出：用户确认不进入本次导入的记录，仍有独立记录和理由。

必须满足“输入记录数＝可导入数＋待确认数＋明确移出数”，每条源记录的ID在去向表中恰好出现一次。一行有三个问题，不能因此算成三条待确认记录。空白行另记位置和数量，不与非空记录混算。

交付要求包含可导入表、待确认表、移出表、逐项变更明细、校验报告和文件清单。变更明细能回答：原值是什么、改成什么、在哪一行列、用了什么规则及版本、谁确认了配置。对于没有变化的输出值，通过来源映射定位原记录，不伪造一条“修改”。

当前基线试验价格为1.9元/一个限定规格任务，同任务的网络重试、平台重试、查询和有效期内领取免费；换来源文件、选表、映射或规则则是新合同、新报价。已知待确认项被正确单列可以属于按合同完成，但不能对用户说“全部记录可导入”。

平台失败包括漏行、错误金额精度、坏文件、缺审计报告或无法按合同交付。最多一次自动重试；可履约后两分钟仍不能形成完整结果，进入失败处置。已收款则退实付，未最终结算则按实际支付能力释放/终止授权，状态准确显示。

## 6. 首版输入和数据边界

| 项目 | 现有基线 |
| --- | --- |
| 格式 | UTF-8 CSV（可带BOM）、XLSX值表 |
| 数据规模 | 1–1000条非空记录，最多20列、5MB |
| 结构 | 一次一个文件，选一个工作表、一行表头 |
| 不接受 | 空表、宏、加密、损坏、公式单元格（含缓存结果）、复杂合并表头、超限文件 |
| 批量与更多结构 | 放P1/P2扩展，需要另定合同和测试 |
| 下载 | 交付结果保留7天，短期签名链接可按权限更新 |
| 原始数据 | 共用规范明确：未购买上传24小时；已购买在交付包生成后24小时清理原始表和临时解析 |
| 报告内的原值 | 逐项审计和问题结果可能含原始值，随结果保留7天；不能承诺24小时清除所有含原数据 |
| 模型用途 | 默认不训练、不公开客户表格；列名和必要样本按最小范围脱敏处理 |

实际清理起点应在各项目文档和界面使用同一规则，并明确失败、取消、长期未结算任务的清理时机。备份仍按共同周期清除，不能把删除在线文件说成已即时清空所有副本。

## 7. 检查发现和改进建议

以下问题不意味着现有文档没有价值，但会影响开发、验收或用户是否愿意购买。未作出的产品决策保持“待冻结”，不擅自写成已同意的新承诺。

| 编号 | 重要性 | 发现 | 建议与通过条件 |
| --- | --- | --- | --- |
| R01 | 上线前必须明确 | 目标系统、模板必填/唯一/长度等规则尚未具体冻结 | 先选一个真实导入场景，或明确首版只承诺自定义标准模板；取得真实导入规范和成功/失败样例 |
| R02 | 正确性阻断 | “订单明细＋实付金额”没有定义金额是每订单还是每商品行；只分币种仍可能重复汇总订单总额 | 定义一行的数据粒度、业务键和每个金额字段的作用范围。若两条商品行都写同一订单100元，不能直接报告200元销售额；不明确时只给单元格解析报告、阻止含业务含义的金额汇总 |
| R03 | 收费前必须明确 | 允许全部记录进入待确认，但未规定可导入数为0时是否仍可收费 | 建议首版默认不对0条可导入的结果收费；如要销售纯诊断报告，另列清晰合同与购买确认，不混称修复成功 |
| R04 | 用户体验关键 | 当前换规则即新报价，用户解决付费结果中的待确认项也可能再次收费 | 定义新需求与同次纠错的边界；可评估同源短期一次补确认或单独重处理方案，先核成本再承诺。程序错误纠错始终免费 |
| R05 | 数据保存关键 | 强调不丢行，但未规定未映射列、用户附带字段以及整行原始信息的交付去向 | 建议预览显示每一列去向，并提供源行对照/未映射列附表或明确允许舍弃的确认；不能把行数守恒等同所有字段无损 |
| R06 | 接口合同关键 | 产物列表的斜杠未明确是同时交付还是任选；多处承诺规范JSON，但可导入数据的JSON文件名/schema未列出 | 冻结每笔SKU必交文件、可选格式、空表输出和JSON schema；若提供importable.json，要实际加入清单、权限及验收，而非只返回行数摘要 |
| R07 | 验收与删除关键 | 项目文档常写“24小时”，共用规范区分上传/交付起点；失败与未结算产物的长期保留界限未落地 | 在界面显示具体到期时间；定义未购买、交付、失败/取消、结算未知四种路径，并覆盖原表/中间值/报告/备份 |
| R08 | 外部依赖待验证 | Machine Pay异步/超时/验付结算尚未完成真实契约实验，1.9元和两周估计无实测支持 | 先跑真实获准SDK的最小服务；确认时序后决定同步或异步。以真实任务和全量成本决定价格，不以文档存在视为已通过 |

此外，默认六字段的哪些必填、数量能否为小数/负数、退款/撤销记录怎样进入目标表、多来源列映射一列时如何冲突，都需要在R01/R02的具体模板中确定，不能留给模型临场决定。

## 8. 我对下一版需求的建议

优先把一个真实导入案例做深：拿到来源表和目标模板，明确一行代表什么、每个字段的约束、每类问题的处理和收费后得到哪些文件。先把R01/R02/R03/R05/R06冻结，再实现受限输入的诊断、确认、付费和交付闭环。批量、更多行业和直接写入外部系统随后扩展。

产品效果至少要用三类证据说明：同一源表的前后对照与行去向、实际目标导入结果、真实用户为节省时间主动购买的反馈。结构检查或功能用例清单不替代这些证据。
