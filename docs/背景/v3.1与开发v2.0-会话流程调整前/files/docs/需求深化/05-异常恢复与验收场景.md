## 参数化维度

每个适用场景按PROVIDED/DISCOVER、支付宝/抖音×Android/iOS、正常/弱网/离开/杀进程、旧/当前版本、本人/其他租户、未付/实付/退款、源/结果有效或到期参数化。不是把42或24行各点一下就算完成，也不机械生成没有业务意义的全组合。

关键边界用小于/等于/大于限制：文件字节、10文件、50处理单元/字段、1000候选、文本5万码点、模板5MB、quote和下载签链到期点、修订余额及并发提交。金额还覆盖0/负数/精度超限/单位不明；空/false/0/缺失要分别测。

## 故障注入顺序与裁决

同一写操作测试提交前断网、已落库但未响应、发件箱未投递、worker执行中断、产物生成未发布、发布后客户端未知六个点。恢复查询同operation/原订单，不再重复创建资源。随机延迟不足以证明竞态正确，需能控制两个请求的提交边界并记录最终资源/副作用数量。

取消/删除/退款与执行发布均要有版本或条件更新守卫；重启不能重新暴露已撤销内容，晚回调不能抹除已付事实。平台错误纠正保留原证据及赔付/退款处理，不用替换合成数据掩盖问题。

## 分级与发布判断

阻断：越权/泄漏、未标记捏造、严重错合/粒度/金额/标识、重复收退、漏源仍称全量、没有实际交付却收费称完成。严重：普通手机流程无法完成、关键错误/按钮被键盘遮挡、B状态误导、无法恢复已确认动作。一般：无语义细节布局偏差。

BLOCKED与未开通不得改PASS；正式不适用要注明规则、范围和关闭开关。先修阻断并复验受影响格式/模式/环境，再决定恢复新单；原有订单查询和售后不能随新单开关一起关掉。
