**项目7：表格修复站——把来源不同的订单表变成可导入、可追溯的数据**

> 历史方案：2026-10-27已由v2.0多源资料按规范成表替代，仅保留背景。当前需求见[PRD](../01-产品需求PRD.md)。

方案日期：2026-10-26。保留原定的数据清洗API方向，建议主投Machine Pay。本文是产品与实现提案，尚未开发、实测或验证付费。价格和时间是待验证假设。

**第一版应解决的具体问题**

首批用户定位为小电商运营、代运营人员，以及为这类用户搭建工作流的开发者。场景是把不同来源的订单表导入同一套管理系统：列名不同、日期格式不同、金额混入符号、订单号被转成数字、疑似重复行导致导入失败。

用户上传源文件和目标字段模板，收到可导入文件、待确认问题、字段映射和变更明细。付费理由应是减少反复修改和导入失败，而非泛泛的“AI帮你处理Excel”。该需求及其价值需访谈验证。

产品核心是付费API；同时提供一个薄网页演示台，方便运营人员预览、确认及领取结果。Agent或工作流使用同一业务服务。网页界面本身不代表已满足Machine Pay接入，参赛必须跑通真实的按量支付链路。

**一个有边界的处理例子**

目标字段为订单编号、下单日期、商品名称、数量、实付金额、币种。

| 源值或情形 | 首版建议处理 | 明确保留的信息 |
| --- | --- | --- |
| “订单号”“订单编码”两个列名 | AI建议映射为订单编号，用户确认 | 原列名、目标列名与确认版本 |
| 文本订单号“000123” | 保持文本及前导零 | 原值和字段类型 |
| Excel已把长订单号截断或丢失前导零 | 标为无法从现文件恢复，要求原始导出 | 不虚构缺失数字 |
| “2026/10/25” | 在确定规则下规范为“2026-10-25” | 原始值和解析规则 |
| “03/04/2026” | 提示月日含义不确定，等待用户选择 | 不自行猜测 |
| “￥1,280.00” | 按明确的人民币、千分位和精度规则解析为1280.00 | 原文、币种和处理依据 |
| “1,280”且地域格式未知 | 确认逗号含义后处理 | 不默认代表1280 |
| 出现两个相同订单号 | 标记候选重复，保留两行 | 不直接认定应删除 |
| 缺失金额或日期 | 保留问题并列入待确认 | 不用模型猜值填充 |

同一订单的多商品行可能有相同订单号，首版应区分“疑似重复”和“用户确认需要移出的记录”。需要去重时，应使用已确认的业务主键与规则。

**首版输入、输出与限制**

首版暂定支持CSV和XLSX，一次一个文件、一个选定数据表、最多1000行和20列、5MB。此范围是为了让定价与交付可控，不是平台官方限制。首版处理值表，包含公式、宏、复杂合并表头或不支持类型时，在付款前说明不支持或要求导出为值。

输入包含源文件、目标字段模板、日期/币种等明确规则。模板可以保存复用，但修改模板会形成新版本。

交付包包含：

- 可导入的CSV/XLSX数据；存在未解决记录时，明确标示为部分可导入结果。
- 待确认记录及其原因，不静默丢失。
- 字段映射、逐项变更明细、原文件行列坐标和规则版本。
- 校验报告：行数去向、金额解析覆盖情况、币种/单位分组汇总、异常明细。
- 供Agent使用的结构化JSON摘要及结果文件领取信息。

用户购买前就能看到问题数量、处理范围及哪些问题需其确认，避免付款后才发现无法完整导入。

**AI只做语义建议，数据计算由规则完成**

AI负责理解列名与用户表达、提出字段映射、识别可能的格式类型、解释异常。默认只发送列名和足以辨别格式的脱敏样本；需要更多真实值时向用户说明。

代码负责类型解析、金额十进制定点处理、日期规则、主键检查、导出和校验。通过用户确认的映射和规则后批量执行，不把1000行完整数据交给模型自由重写。无法证明的修正应保留为待确认。

完整可追溯记录至少包含文件指纹、表名、源行列、原值、输出值、规则编号与版本、用户确认内容。相同输入和规则应产生相同业务结果。

**校验必须说清楚“校验了什么”**

行数校验建议采用：输入记录数＝可导入记录数＋待确认记录数＋经用户确认移出的记录数。每条源记录须有且仅有一个最终去向。

金额仅对明确币种、明确单位、可成功解析的相同业务字段汇总；不同币种不直接相加，也不把多个不同含义的金额列混为一项。报告同时列出未解析金额的记录数。数量×单价是否应等于实付金额要由业务规则说明，不能在有优惠、运费等情形下强行要求相等。

这些校验用于发现转换错误，不代表原始订单事实正确，也不替代财务或税务判断。

**付费流程与Machine Pay接入**

首版定价假设为1.9元/一个限定规格文件任务；只发布一种固定规格服务，先避免多档价格增加开通和计费复杂度。[Machine Pay官方产品说明](https://aipay.alipay.com/products/machine-pay)

建议用户路径：上传并检查规格 → 免费查看诊断和字段映射建议 → 确认规则及待确认处理方式 → 获得确定报价 → 发起付费服务调用 → 按官方402流程完成授权、验付与结算 → 执行或交付处理结果。

官方产品说明包含HTTP 402付款要求、付款处理及凭证校验流程。实际请求字段、SDK、中间件、校验和结算顺序按接入文档与沙箱结果落地，不自行发明支付凭证或协议字段。

下面是业务接口的建议划分，并非支付宝API名称：

| 业务动作 | 作用 | 费用设计 |
| --- | --- | --- |
| 上传与预检查 | 验证文件规格与可读性 | 免费，限制频率 |
| 查看与确认映射 | 确认目标列、日期/币种和歧义处理 | 免费，控制模型样本规模 |
| 提交处理 | 使用固定服务规格与已确认规则请求处理 | 每个新任务1.9元 |
| 查询与领取 | 查询已有任务、领取已付款交付物 | 同一任务不再收取 |

异步任务及结果领取是本产品的业务设计；能否通过所选Machine Pay接入方式以该模式交付，要在沙箱先验证。若接口只适合同步返回，首版可先限制输入规模同步交付结果，再扩展后台任务。

任务绑定所属用户、原始文件指纹、目标模板版本、确认规则版本及报价版本。幂等标识按用户和请求作用域保存，避免同一付款重试重复收费或执行；不能因全局文件内容相同就让另一用户领取其结果。换文件或规则属于新任务，重新明确报价。

支付失败不放行交付；付款成功但处理失败需要有限重试与退款处理；退款到账状态单独查询。重复通知、网络超时后重试、同一凭证请求不同文件和并发重复提交应作为重点验证场景。

**四项初赛指标的机会与短板**

| 维度 | 应提供的证据 | 主要短板 |
| --- | --- | --- |
| 产品完整度30% | 源表、目标模板、确认映射、可导入文件与变更校验报告 | 泛化过大，无法稳定处理真实杂乱文件 |
| 支付集成度25% | Agent调用遭遇付款要求，用户确认后完成付费处理并领取结果 | 只有网页收费，未跑通真实Machine Pay链路 |
| 商业化成熟度25% | 多个独立付款者的有效交易及真正完成的数据任务 | 少数企业客户重复大量调用，去重付费用户仍少 |
| 作品影响力20% | 可公开运行的合成样例、导入前后结果、开发者对接与用户反馈 | 正式客户数据难以公开，产品视觉效果偏弱 |

官方评分与统计口径见：[活动细则](https://render.alipay.com/p/yuyan/180022670000190962/index.html#/activity-rules)。需要向官方确认具体Machine Pay交易的归属、去重及退费统计规则，不能把API调用次数直接当作付费用户数。

**为何用户可能会买，如何验证**

潜在用户可能已经使用表格公式、现有软件或自己的脚本。访谈应要求其展示最近一次导入失败，记录问题、耗时和现有处理方式，不能只询问是否喜欢AI清洗。

差异化假设是：更快配置跨来源映射、批量复用、每处修改可追溯、处理结果有清晰校验、Agent可直接按需调用。只有这些能力比用户原流程更省事时，1.9元按次收费才有意义。

七天验证可按以下顺序：前2天接触10—15位有真实导入需求的运营或开发者；中间2天收集5种脱敏文件与目标模板；后3天交付受限测试，让用户确认能否导入目标系统、还需多少手工处理，并观察真实购买。

内部决策线可以设为：至少3个独立用户愿意为其真实任务购买，且交付后至少2个完成目标导入；所有已支持的变换均可解释，未解决项清楚列出。这是需求试验建议，不是赛事计分门槛，也不证明大规模市场需求。

样例演示可公开一份含格式混用、前导零、歧义日期和重复候选的合成订单表。报告应显示实际处理结果与未解决项，不能用少量成功行冒充全文件处理成功。

**成本、实现与质量验证**

1.9元是假设价格。单笔贡献＝售价－预检查及模型推理分摊－处理和存储－支付费－失败重试及售后成本；人工支持与固定开销另计。示例：总变动成本0.3元时贡献1.6元，成本1元时贡献0.9元。这些成本数字仅用于敏感性分析，并非当前供应商报价。

低价API的人工支持成本可能高于推理成本，所以首版重点是固定规格、良好错误提示和可重复的规则。免费预检与未付款用户成本应一起计入。

技术方向：轻网页演示台、Python文件解析与规则引擎、数据库中的用户/订单/规则/任务记录、官方Machine Pay接入适配、受控文件存储。可以使用Windows原生进程实现，不需本地Docker或WSL。输出值、字段类型及文件有效性需由实际文件验证。

建议建立有标准答案的小样本集，覆盖前导零、超长ID、金额符号与精度、日期歧义、重复订单多商品行、缺失值、坏文件、边界行数与编码。还应验证行数去向、同币种金额保持、映射版本变化以及支付幂等。该项目会改变业务数据，正确性验证是首版必要工作。

原始文件与结果的保留策略在上传前说明。例如原文件24小时后删除、结果7天可领取，并提供提前删除入口；这些是待实施策略，不能在未实现时向用户承诺已自动删除。客户数据默认不用于公开演示。

按1—2名熟悉网页和数据处理的开发者估计：第1周完成限定输入、映射、规则、导出和校验；第2周完成沙箱支付、幂等、结果领取、异常处理及首批线上验证。审批与外部产品开通时间不包含在该估计内。

**判断**

该方向更能展示Agent按量购买专业数据能力的过程，规则和校验也便于工程验证。最大商业挑战是付费意愿与获客：高调用量可能来自极少数付款者，不能自动带来赛事中的去重用户优势。应先用真实导入任务验证省时与可靠性，再扩展为通用清洗平台。
